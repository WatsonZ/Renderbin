# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-user file hosting/sharing tool. Users log in (accounts live in the `users` table; the first account, id=1, created via the first-run welcome page, is the super admin — registration of further accounts is a config toggle), upload files — `.html` (served verbatim), `.md`/`.markdown` (rendered to HTML), or `.txt` (shown as HTML-escaped preformatted text) — stored as text in SQLite, never on disk, and marks each one public or private. A file's format is recorded in its `kind` column (`html`/`markdown`/`txt`) and fixed at creation; the raw source of every kind lives in the `html_content` column regardless. Public files are viewable by anyone with the file's access code (`/res/{slug}?code=...`); private files require an active session. It's a monorepo: a Go API backend and a SvelteKit SPA frontend, built as a single deployable binary/container.

## Commands

Run everything from the repo root via the `Makefile` (each target just `cd`s into `backend/` or `web/`):

```
make dev-api      # go run ./cmd/server (backend on :8080; reads/creates data/app.db — no credential env vars, the first user is created on the welcome page)
make dev-web      # pnpm run dev (Vite dev server on :5173, proxies /api and /res to :8080)
make build-web    # pnpm run build, then copies web/build/* into backend/internal/web/dist
make build-api    # go build -o bin/server ./cmd/server
make build        # build-web + build-api (produces a single self-contained binary)
make check        # frontend: svelte-kit sync && svelte-check; backend: go vet ./...
make sqlc         # regenerate backend/internal/db/sqlcgen from queries + migrations
make test         # frontend vitest + backend go test
make tidy         # go mod tidy
```

For local full-stack dev, run `make dev-api` and `make dev-web` in separate terminals — the Vite dev server proxies API/backend routes so the frontend never needs CORS handling.

To run a single test:
- Backend: `cd backend && go test ./internal/auth/... -run TestName`
- Frontend: `cd web && pnpm exec vitest run src/lib/schemas/login.spec.ts` (or `-t "test name"`)

Frontend-only commands (run from `web/`): `pnpm run lint` (prettier --check + eslint), `pnpm run format` (prettier --write).

Docker: `docker compose up -d` pulls the published image and starts it bound to `127.0.0.1:8080`, expecting an Nginx reverse proxy in front in production. To build the image locally instead: `docker build -t renderbin:dev .`.

## Architecture

**Single-binary deployment model.** The frontend is a static SvelteKit SPA build; `make build-web` copies its output into `backend/internal/web/dist`, which is embedded into the Go binary via `//go:embed` (`backend/internal/web/web.go`). The compiled server serves both the API and the static frontend — there is no separate frontend server in production. Nothing under `backend/internal/web/dist/` is tracked except its `.gitignore` -- that one file is enough for `//go:embed all:dist` to compile on a fresh clone (the SPA 404s until you run `make build-web`, which is the honest outcome). It used to track `index.html` as a "placeholder", but `make build-web` overwrote it with real, hash-referencing build output, so every frontend build dirtied a tracked file and a fresh clone produced a binary serving a page whose assets 404.

**Backend layout** (`backend/`, module `github.com/shawn-bluce/renderbin/backend`):
- `cmd/server/main.go` — entrypoint; wires config (`LISTEN_ADDR`, `DB_PATH` via `envOr`, both defaulted — there are **no credential env vars**; accounts live in the `users` table), opens the DB, builds the router, starts `http.ListenAndServe`.
- `internal/db/` — `db.go` opens the SQLite connection (via `modernc.org/sqlite`, pure Go, no CGO), enables WAL mode, and runs a hand-rolled migration runner: it reads `internal/db/migrations/*.sql` (embedded), applies any file not yet recorded in a `schema_migrations` table, in filename sort order, each in its own transaction. Add new schema changes as a new numbered file (e.g. `0002_*.sql`), never edit an already-applied one. `0001_init.sql` is the whole schema: the seven incremental migrations that predated the first release were squashed into it, verified by regenerating `sqlcgen` from both the old and the squashed set and diffing (byte-identical). It preserves the column order those ALTER TABLEs produced, which is why `files` reads oddly -- `deleted_at` mid-table, `kind` near the end. The one intentional change was dropping `DEFAULT 1` from `files.user_id` and `sessions.user_id`: that default was a backfill artifact, and a silent fallback owner is worse than a NOT NULL failure. `internal/db/queries/*.sql` holds sqlc query annotations; `internal/db/sqlcgen/` is **generated** (`make sqlc`) — don't hand-edit it. There's no ORM by design.
  - `files.sql` is split into two banner-marked sections. Everything in **OWNER-SCOPED** carries `user_id = sqlc.arg(user_id)`; new file queries go there and must carry it. The **UNSCOPED** section exists only for the anonymous `/res/{slug}` render path (`GetFileBySlugAnyOwner` plus the counter bumps) — the name says the hazard, and nothing behind `requireAuth` may call it.
  - **Keep the query files pure ASCII.** sqlc's SQLite rewriter substitutes parameters by byte offset while the parser reports character positions, so a single multi-byte character in a comment silently corrupts codegen — you get parse errors about mangled tokens like `SELid` or `nam?1` pointing at innocent lines.
- `internal/auth/` — pure, DB-free credential/token/cookie mechanics: `HashPassword`/`VerifyPassword` (bcrypt, for `users.password_hash`), `BurnPasswordCheck` (spends one bcrypt compare when the username doesn't exist, so login timing doesn't leak username existence), `NewSessionToken`/`NewAccessCode`/`NewAPIKey` (crypto/rand; API keys are `rb_` + 48 hex chars), `SetSessionCookie`/`ClearSessionCookie` (`rb_session`, HttpOnly/Secure/SameSite=Lax, explicit `Expires`/`MaxAge` matching `SessionTTL` = 30 days).
- `internal/handlers/` — HTTP handlers, one file per resource: `auth.go` (login/register/logout/me; registration is gated on the `allow_registration` config and auto-logs the new user in), `setup.go` (first-run status + super-admin creation, only valid while the users table is empty), `settings.go` (global configs — readable by any logged-in user, writable only by the super admin (id=1, `IsSuperAdmin`) — plus profile nickname/password updates and the per-user MCP API key ensure/reset), `mcp.go` (the MCP server, see below), plus `session.go` holding the identity helpers (`CurrentUser`, `WithUser`, `requireUser`) and `content.go` holding the kind constants (`KindHTML`/`KindMarkdown`/`KindText`) and the `renderContent` logic that turns a file's stored source into the bytes served by `Render` (html verbatim; markdown via goldmark into a styled, self-contained page; txt HTML-escaped inside a `white-space: pre-wrap` `<pre>`). Markdown runs goldmark with GFM **and raw-HTML passthrough enabled** — deliberate, since the `html` kind already serves uploader-authored HTML verbatim, so uploaders are trusted authors and sanitizing markdown would buy no safety that kind doesn't already give away. Handlers take the generated `*sqlcgen.Queries` and a `*slog.Logger`. Config keys (`allow_registration`, `mcp_enabled`) are defined in `auth.go`; boolean configs store `"true"`/`"false"` in the `configs` table and read as false when missing.
- `internal/server/server.go` — assembles the chi router:
  - `/api/health`, `/api/setup/status`, `/api/setup`, `/api/auth/{login,register,logout,me}` — public (setup 409s once a user exists; register 403s unless `allow_registration` is on).
  - `/api/files*` (list/create/rename/toggle-visibility/refresh-code/soft-delete, plus `GET /api/files/search` — own-files substring search, see frontend notes), `/api/settings` (GET any user / PUT super admin only), `/api/user` (PATCH nickname/password; password changes require the current password), `/api/user/api-key[/reset]` (POST; 409 unless `mcp_enabled`), `/api/backup` (GET, **super admin only** — the snapshot is the whole DB) — behind the `requireAuth` middleware, which 401s without a valid session cookie *and* resolves it to the user, stashing it in the request context. Handlers behind it call `requireUser(w, r)`; the two routes outside it (`/api/auth/me`, `/res/{slug}`) resolve the cookie themselves via `CurrentUser` — which is also why the identity helpers live in `handlers` rather than `server`, avoiding an import cycle since `server` already imports `handlers`.
  - `/res/{slug}` — the public file-viewing endpoint (`FilesHandler.Render`), gated by its own logic rather than middleware: 404 if missing/soft-deleted (checked *first*, so a valid session can never resurrect a deleted file); else a valid session bypasses everything; else `is_public` + a `?code=` matching `access_code` (compared with `crypto/subtle.ConstantTimeCompare`) serves it; else 403. What gets served on success depends on the file's `kind` (see `content.go`), but access control is identical across kinds. The authenticated `/api/files/{slug}/download` returns the untransformed source (not the rendered form) with a kind-appropriate extension/Content-Type. Every access to an existing (non-deleted) file bumps `files.success_count` or `files.failure_count` accordingly — this is analytics, not a content edit, so it deliberately does **not** touch `updated_at`. A 404 for a slug that never existed increments nothing (there's no row to attribute it to).
  - Catch-all SPA handler serving embedded static files, falling back to `index.html` for unknown paths (client-side routing).
- `internal/web/` — embeds the built frontend.

To add an endpoint: write the SQL in `internal/db/queries/`, run `make sqlc`, write a handler using the generated `Queries` methods, register the route in `internal/server/server.go`.

**Sessions are DB-backed** (a `sessions` table with a `user_id` column, not an in-memory map) so logins survive process restarts/redeploys — consistent with this app's "all state lives in SQLite/volumes" model. There's no session cleanup cron; expired rows are opportunistically deleted on each login, and `GetValidSession` filters `expires_at > CURRENT_TIMESTAMP` in SQL so an expired token is never treated as valid even before that sweep runs. Changing a password does **not** invalidate existing sessions (they're looked up by token only) — to force every session to log out immediately, manually run `DELETE FROM sessions` against the SQLite file.

**Users and configs.** The `users` table holds `username` (unique), `nickname`, `password_hash` (bcrypt), and a nullable per-user `api_key` (created lazily when MCP is enabled and the user visits settings; reset always issues a fresh one). The super admin is **id=1 by convention** (`handlers.SuperAdminID`) — the first row created wins, whether via `/api/setup` or a seeded test. The `configs` table is a generic TEXT key/value store; current keys are `allow_registration` and `mcp_enabled`. `files.user_id` records the uploader (all pre-migration rows were backfilled to user 1) and **every** file path is scoped by it — web, search and MCP alike, with **no super-admin exception** (id=1 only gains the global config toggles and `/api/backup`). `api_key` is stored in plaintext; that's a recorded deferral, not an oversight — it stopped being an escalation path once `/api/backup` became super-admin only, and hashing it would force the settings page from "view your key any time" to "shown once at creation", which is a product decision to make on its own.

**MCP server** (`internal/handlers/mcp.go`, mounted at `/mcp` in server.go — outside `/api` and the session middleware). Built on the official `github.com/modelcontextprotocol/go-sdk` (v1.2.0, pinned; pure Go — a discussed, accepted dependency): stateless streamable HTTP (`Stateless: true, JSONResponse: true`), so every `tools/call` POST is self-contained (no initialize handshake, no session state, GET/DELETE are 405). Layering: 32MiB `http.MaxBytesReader` cap (the SDK reads whole messages into memory and has no cap of its own) → `mcp_enabled` config gate (403 when off) → SDK `auth.RequireBearerToken` (imported as `mcpauth`; 401 on bad keys) → MCP server. The verifier resolves the Bearer token via `GetUserByAPIKey` and smuggles the user row plus the request-derived base URL (`X-Forwarded-Proto`/`-Host` aware) to tool handlers through `TokenInfo.Extra` / `req.Extra.TokenInfo` — v1.2.0 rejects zero-expiration tokens, so the verifier sets a dummy 1h expiration (keys don't actually expire). Six typed tools (`mcp.AddTool`, schemas inferred from struct tags; returned errors become tool errors, not protocol errors), all scoped to the key owner's files (`ownedFile` wraps `GetUserFileBySlug`, so a missing slug and a foreign one are literally the same case — no row — and both yield "file not found in this project"): `upload_file`/`upload_files` (markdown/html only — stricter than the web API's `normalizeKind` — created **private**, batch capped at 20), `search_files` (name+content via `SearchUserFilesWithContent`), `update_file` (name/content only; slug/kind/access-code immutable over MCP), `publish_file` (sets `is_public`), `delete_file` (two-phase: without `confirm` it only returns the file's name+URL for the user to confirm; with `confirm=true` it soft-deletes — `HardDeleteFile` is deliberately unreachable over MCP). Upload reuses `createFileWithFreshSlug` (extracted from `FilesHandler.Create`).

**Frontend layout** (`web/`, SvelteKit 2 + Svelte 5): pure SPA — `ssr` is disabled globally (`src/routes/+layout.ts`), and `@sveltejs/adapter-static` is configured with `fallback: 'index.html'` (see `vite.config.ts`; there is no separate `svelte.config.js` — adapter/compiler options live in the `sveltekit()` vite plugin config). Components use Svelte 5 runes (`$state`, `$props`, etc.) exclusively — no Svelte 4 patterns, no Redux/Zustand-style stores. Directory convention: `src/lib/api/` (fetch wrappers around backend endpoints), `src/lib/schemas/` (zod schemas), `src/lib/components/`. Forms use `sveltekit-superforms` in **SPA mode** (`superForm(..., { SPA: true, validators: zodClient(schema) })` with the `zod4`/`zod4Client` adapters from `sveltekit-superforms/adapters` — this project uses zod v4, and the plain `zod`/`zodClient` exports from that package are for zod v3) since there's no SvelteKit server to host form actions. Styling is Tailwind v4 (CSS-first config via `@theme` in `src/routes/layout.css`, no `tailwind.config.js`). Icons come from `@iconify/svelte` + `@iconify-json/lucide`; add other icon sets only when a design actually needs them. `src/lib/icons.ts` registers the whole Lucide set into `@iconify/svelte`'s in-memory store via `addCollection` (imported once, as a side effect, from the root `+layout.svelte`) — without it, `<Icon icon="lucide:...">` falls back to fetching from the public Iconify API at runtime, which is wrong for a self-hosted app with no guaranteed internet access. This costs ~90KB gzipped in the root layout chunk; fine at this app's scale — revisit with per-icon subsetting only if that ever actually matters. Fonts are `@fontsource-variable/inter` (sans) and `@fontsource-variable/jetbrains-mono` (mono, used for slugs/HTML source). The whole app is a fixed dark theme (`color-scheme: dark` + `bg-neutral-950` on `body` in `layout.css`) — there's no light-mode toggle.

The root `+layout.ts` is also the auth guard for the whole SPA: it first fetches `/api/setup/status` — while no user exists every route redirects to `/welcome` (the first-run page that creates the super admin and picks the initial `allow_registration`/`mcp_enabled` configs); once set up, `/welcome` redirects to `/login`, `/login` and `/register` stay public, and every other route `fetch('/api/auth/me')`s, redirecting to `/login` on a 401. The guard returns `{ user, allowRegistration }` as layout data — pages read the current user from there rather than re-fetching. `/settings` (linked from the dashboard top bar) has three sections: profile (nickname + password change, any user), registration toggle and MCP toggle (rendered for everyone but disabled for non-super-admins), and — when MCP is on — the per-user API key with copy and a confirm-modal-guarded reset. Shared UI: `src/lib/components/Toggle.svelte` (controlled switch; the parent flips state only after the API call succeeds). `src/routes/+page.svelte` is the file-management dashboard (`+page.ts` preloads the list); it links to `/res/{slug}?code={access_code}` with `target="_blank"` + `data-sveltekit-reload` (that path is served by the Go backend, not a SvelteKit route — same reasoning as the `svelte/no-navigation-without-resolve` eslint-disable next to it). Internal navigations (`goto`) use `resolve()` from `$app/paths` per that same lint rule.

The public/private filter and sort (by name/success-count/failure-count, both directions) are client-side over the already-fetched file list. Search is **not**: the search bar above the list calls `GET /api/files/search?q=…&content=true|false` (250ms debounce, sequence-numbered so stale responses are dropped), which does a substring search over the *current user's own* non-deleted files — name-only by default, plus `html_content` when the "搜索正文" toggle next to the box is on. A name hit renders as a plain row; a content-only hit also returns a `snippet` (the match ±100 runes, ellipsized, built by `contentSnippet` in `internal/handlers/files.go`) that the row shows as de-emphasized text. Result rows are joined back against the local `files` array (`searchRows`), so optimistic mutations (rename/delete/visibility) reflect immediately; the visibility filter and sort also apply to results, always as a flat list. Picking an explicit sort key drops the default day-grouped ("Today"/"Yesterday"/…) view in favor of a flat sorted list, since grouping by day and sorting by name/counts at the same time isn't a coherent combination; "Recent" is the only mode that groups (and search results never group). The row markup is a `{#snippet fileRow(file, trashed, excerpt?)}` reused by the grouped, flat, and search render paths — extend it there rather than duplicating the `<li>` markup if any path needs to change.

**Deployment**: single `Dockerfile` (multi-stage: node/pnpm build → golang build with `CGO_ENABLED=0` → alpine runtime) and `docker-compose.yml` with one named volume, `db-data` → `/data`, holding `app.db` and its WAL sidecars — mount the directory, never the single file, or `app.db-wal` ends up outside the mount. (There were once `backup-data`/`log-data` volumes reserved for `internal/backup`/`internal/cron`; nothing ever wrote to them — backups stream a `VACUUM INTO` snapshot straight to the browser and logs go to stdout — so they were removed. Re-add them if a cron-driven, writes-to-disk version ever lands.) The compose project `name:` is pinned so the volume name doesn't change when the checkout directory is renamed. `stop_grace_period` is 15s, just above the server's own 10s shutdown deadline. The container binds to `127.0.0.1:8080` only; a host Nginx is expected to reverse-proxy to it. Log rotation is configured on the `json-file` docker logging driver (`max-size`/`max-file`), not in-app. Upgrades are `docker compose pull && docker compose up -d`; all state lives in the volume, and migrations are forward-only, so rolling back to an older image needs a restored backup, not just an older tag.

**Releasing.** Pushing a `vX.Y.Z` tag runs `.github/workflows/release.yml`: verify (same checks as CI) → publish a multi-arch image to `ghcr.io/shawn-bluce/renderbin` and attach static linux amd64/arm64 binaries to a GitHub Release. Nothing is published without a tag. Three things about it are load-bearing:

- **Both Dockerfile build stages are pinned to `--platform=$BUILDPLATFORM`, and the Go build takes `ARG TARGETARCH`.** So a multi-arch build never runs under QEMU: the frontend is built once (its output is architecture-independent) and the backend cross-compiles for free, since `CGO_ENABLED=0` plus the pure-Go SQLite driver make arm64 just a different `GOARCH`. Verified locally — buildkit reports the second pass as `[linux/arm64->amd64 backend-build]`, i.e. cross-compiling, and only the tiny runtime stage exists per platform. Don't add `setup-qemu-action`; it would make the build an order of magnitude slower for nothing.
- **`docker-compose.yml` deliberately has no `build:` key.** With both `build` and `image`, compose *builds* when the image is missing locally instead of pulling — silently undoing the point of publishing images.
- **The container runs as uid 10001 and `/data` is pre-created with that owner in the image.** Docker copies a named volume's initial ownership from the image directory it shadows, and only when it first creates the volume. A volume created by an older root-running image stays root-owned and the server can't open its database; fix with `docker run --rm -v renderbin_db-data:/data alpine chown -R 10001:10001 /data`.

**Version stamping.** `internal/buildinfo.Version` is set with `-ldflags -X` — by the Git tag in releases, by `git describe` in `make build`, and left as `"dev"` for a plain `go build`. It's read by `/api/health`, the MCP `Implementation`, and the startup log line. `runtime/debug.ReadBuildInfo`'s VCS stamping isn't an option: it needs `.git` in the build context, which `.dockerignore` excludes on purpose.

## Stack decisions to preserve

These were deliberate choices (see git history / original spec) — don't reintroduce the excluded alternatives without discussing it first:
- **Ownership is enforced in SQL, not in Go.** Every file query reachable from `requireAuth` filters on `user_id`, so a foreign slug simply matches no row. Don't "simplify" this into a Go-side check before an unscoped query: `emit_interface: false` means dropping a `user_id` predicate breaks the build at every call site, whereas a forgotten Go check compiles fine. Caveat worth knowing — that guarantee is strong for scalar-arg queries but weaker for `...Params` structs, where a literal may legally omit the new field; `TestFileQueriesRejectForeignOwner` and `TestFileEndpointsCoverAllRoutes` cover that gap.
- **Status codes: 404 when the question is "does this object exist", 403 when it's "may this role use this known, public endpoint".** So a foreign or missing slug is an identical 404 everywhere (slugs are ~24 bits and half the credential for `/res/{slug}?code=`; a 403 would make any account a slug oracle), while `/api/backup` and `PUT /api/settings` answer 403. Known residual: `files.slug` is globally UNIQUE, so renaming onto a stranger's slug still 409s — an existence oracle inherent to a global slug namespace, accepted rather than fixed.
- No ORM (GORM/ent) — sqlc-generated code + raw SQL only.
- No CGO SQLite driver — `modernc.org/sqlite` only, so cross-compilation and the alpine runtime stay simple.
- Markdown rendering is `github.com/yuin/goldmark` (pure Go, no CGO — consistent with the SQLite-driver choice). Don't swap in a CGO-based renderer (e.g. cmark bindings). Rendering happens server-side in `Render`; there's no client-side markdown library.
- No Redux/Zustand-equivalent frontend state library — Svelte 5 runes only.
- No microservices, no message queue, no Redis/cache layer.
- Auth is hand-rolled on `golang.org/x/crypto` (bcrypt), not a third-party auth service — users live in the `users` table (no env-var credentials; don't reintroduce `ADMIN_USERNAME`/`ADMIN_PASSWORD`), the super admin is id=1 by convention, and registration is gated by the `allow_registration` config. Don't add a "forgot password" flow, email verification, roles beyond the id=1 super admin, or login rate-limiting without discussing it first; these were explicitly scoped out (bcrypt's own per-attempt cost is the accepted mitigation for no rate-limiting). No CSRF token either — `SameSite=Lax` on the session cookie is the accepted mitigation.
- `internal/cron`, `internal/backup`, `internal/ratelimit` are still-reserved package names for functionality to add as needed (`internal/auth` is now implemented) — don't invent different locations for that logic later.
